# Step 1.9 findings review

Step 1.9 appends an immutable review-set record before entering the operator wait. It binds the run, findings-review execution, exact document version, ordered finding membership, membership hash and count. Server reads and submissions use only that membership; later or historical findings cannot enter it.

Findings and dispositions are append-only. `hard_flag` is persisted application-owned data; attribution/provenance inventory findings are marked by the application rather than inferred in the UI. Each row exposes producing step, full location, issue, evidence, suggested fix and rule reference.

A submission must carry an idempotency key and an explicit decision for every finding in the frozen set, including deterministic fact-verifier findings and the `fact.advisory_unavailable` warning when Step 1.7 model output was unusable. Its canonical payload hash includes trimmed rationale (blank becomes null); a reused key with different payload, or any cross-run key collision, is a typed conflict. One database transaction records dispositions and the auditable review submission, completes the active Step 1.9 execution, advances to Step 1.10 and creates or reactivates the durable queue job. The in-memory repository provides transaction-equivalent rollback for this boundary, including the exact execution, run and parked queue state when enqueueing fails. A production route returns `202` with `continuation: "queue_accepted"` after that commit; it never invokes milestone four synchronously. Same-payload replays are observational and return `200` with `continuation: "already_accepted"`. The old synchronous continuation exists only behind the explicit `testOnlySynchronousPipeline` composition switch for isolated tests.

An empty review set records a zero-count review submission and completes 1.9 without a human interruption. The ingest path then continues through the existing milestone-four orchestration. SERP warnings remain informational and never gate this transition.
